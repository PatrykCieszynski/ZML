# ZML Game Bridge — Short MVP Roadmap

## P0 — Stabilność DB / runtime

1. **~~API posty nie mogą robić write do SQLite~~**
   - ~~GET routes mają mieć tylko read access.~~
   - ~~POST/PUT/PATCH/DELETE mają tworzyć runtime command/input.~~
     - ~~Run write path idzie przez RuntimeInputQueue -> MiningCoordinator -> DbWriter command queue.~~
     - ~~Mining tools write path idzie przez RuntimeInputQueue -> MiningCoordinator -> MiningSetupService.~~
   - ~~DbWriter ma zostać jedyną ścieżką zapisu czegokolwiek do bazy.~~

2. **~~Rozdziel SQLite connections~~**
   - ~~`open_writer_connection()` tylko dla `DbWriterWorker` / startup migration.~~
   - ~~`open_read_connection()` dla API GET, najlepiej `mode=ro`.~~
   - ~~Nie odpalaj `ensure_schema()` w read dependency.~~

3. **~~Zmień shutdown z `qsize()` na close/sentinel/drain~~**
   - ~~Najpierw zatrzymaj producers.~~
   - ~~Potem drain runtime input channel.~~
   - ~~Potem drain event channel.~~
   - ~~DbWriter ma zamknąć connection w `finally`.~~

4. **Domknij lifecycle backendu Pythonowego w Electronie**
   - Brak orphan processów i wiszących DB connection przy zamykaniu UI/backendu.
   - Naprawić przypadki `Waiting for background tasks to complete`.

5. **~~Health state workerów~~**
   - ~~Minimalnie: running/degraded/crashed/stopped.~~
   - ~~DB writer/OCR/input coordinator crash ma być widoczny w `/health`.~~

6. **~~Drop visibility bug / active map circles~~**
   - Dropy są trwałą historią runa/segmentu i nie mogą znikać ze statystyk.
   - Kółka z mapy mogą znikać, ale nie statystyki runa.
   - Aktywność kółek dropów powinna być UI visibility/TTL, nie backendowym usuwaniem dropów.
   - Run/segment stats muszą liczyć z durable drop history, nie z active map drops.
   - Widoczność kółek powinna odświeżać się sama co kilka sekund, nie tylko po nowym dropie.

## P1 — Segmenty, claimy, loot

7. **~~Segment lifecycle~~**
   - ~~Nowy segment zamyka stary aktywny segment.~~
   - ~~Zmiana finder/ammo/mode/probes tworzy nowy segment.~~
   - ~~Identyczny setup nie tworzy duplikatu segmentu.~~
   - ~~Extractor jest globalny, nie segmentowy.~~

8. **~~Segment snapshot~~**
   - ~~Segment ma zapamiętać finder, ammo, probes, mode.~~
   - ~~Snapshot ma być wyświetlany w UI.~~

9. **~~Claimy muszą wpadać do segmentów~~**
   - ~~Do runów już wpadają.~~
   - ~~Claim powinien dostać segment z dropa/kontekstu, nie z aktualnego segmentu przy extract.~~

10. **~~Extracted claimy nie mogą znikać ze statystyk~~**
   - ~~Active claims zostają jako aktywna lista.~~
   - ~~Extracted claims mają być w historii/statystykach.~~
   - ~~Expiration bardziej pod mapę, nie blokuje MVP.~~

11. **~~Loot aggregation~~**
   - ~~Loot agregować podobnie jak claimy.~~
   - ~~Minimum: per run, per resource/item.~~

12. **~~Claim extracted event w Dashboardzie~~**
   - ~~Dashboard chyba powinien pokazywać extract claimu jako event?~~

13. **~~Safe delete run~~**
   - ~~Nie usuwać fizycznie.~~
   - ~~Markować jako ignored/deleted.~~
   - ~~Ukrywać z UI/statystyk domyślnie.~~
   - ~~Wymaga confirmation.~~

## P2 — OCR / config / dane testowe

14. **~~Przerzucić ROI do configu~~**
   - ~~Finder/compass/deeds/loot ROI nie powinny siedzieć hardcoded w kodzie.~~
   - ~~Na MVP wystarczy config/profile, bez UI kalibratora.~~

15. **~~Finder OCR: migracja z `pytesseract` na `tesserocr`~~**
   - ~~Chcemy jedną instancję OCR na workera.~~
   - ~~Usuwamy runtime path oparty o `pytesseract`.~~
   - ~~OCR worker ma używać małego wrappera wokół `tesserocr`, żeby nie rozlewać biblioteki po kodzie.~~

16. **~~Recording screenshotów findera~~**
   - ~~Potrzebne do testowania OCR frameworków.~~
   - ~~Zapisywać crop + metadata.~~
   - ~~Tryby: manual, low-confidence, state-change, every N seconds.~~

17. **~~Profilowanie OCR~~**
   - ~~Zmierzyć capture/crop/preprocess/ocr/parse/emit.~~
   - ~~Zakładamy, że OCR jest głównym latency cost dla drop eventu, ale najpierw mierzymy.~~
   - ~~CPU jest już niskie po zwiększeniu delayu, problemem jest raczej delay między dropem a eventem.~~

18. **Compass latest-wins**
   - Max pending job = 1.
   - Drop stale frames.
   - Latest result wins.
   - Starszy OCR result nie może nadpisać nowszej pozycji.

19. **Radar/position outlier filtering**
   - Pojedynczy błędny odczyt nie może przerzucać pozycji o tysiące kratek.
   - Odrzucać outliery względem ostatniej stabilnej pozycji.
   - Dodać max movement threshold per time window.
   - Oznaczać suspect/rejected readings w debug logach.

## P3 — UI / dashboard

20. **~~Napraw dashboard filters~~**
   - ~~Aktualnie filtry nie działają.~~

21. **Quick finder change w active setup**
   - Po lewej fajnie byłoby szybko zmieniać finder.
   - Zmiana musi iść przez runtime command, bo wpływa na segment.

22. **Pozycja w lewym dolnym rogu**
   - Pokazać latest position w głównym oknie.
   - Nie musi update’ować się tak często jak mapa.
   - Nie zapisujemy streamu pozycji do DB.

23. **Scrollbar w portrait/narrow mode**
   - Jak width za mały, UI musi być scrollowalne.

24. **Custom scrollbar theme**
   - Defaultowy scrollbar jest brzydki i nie pasuje.
   - Nice-to-have, nie blokuje MVP.

25. **Electron left click**
   - Sprawdzić, czy wystarczy normalny DOM click/pointerdown.
   - Electron-level handling tylko jeśli naprawdę potrzebne.

## Later / po MVP

- Po profilowaniu OCR rozważyć przeniesienie ciężkich OCR pipeline’ów z wątków do osobnych procesów.
- Electron docelowo orchestruje start/restart/close `game-bridge`.
- Automatyczna zmiana planety.
- Hexgrid:
  - tryb no-overlap,
  - tryb max-coverage,
  - offset anchor na graczu,
  - orientacja vertical/horizontal.
- Sygnał dźwiękowy, gdy claim jest mniejszy niż user-defined threshold.
- Więcej settingsów w UI:
  - Hz/interwał dla kompasu,
  - Hz/interwał dla deeda,
  - Hz/interwał dla findera,
  - czas aktywności kółek dropów.
- History View dla claimów z zakresem dat.
- Export run/history do CSV/JSON.
- Debug view dla raw OCR/events.
- Po 1.0 rozważyć wydzielenie OCR do managed local worker process - bardziej mikroserwisowe podejście - czystszy kod lepszy rewrite jeżeli kiedykolwiek powstanie oficjalne API..
  Najpierw OCR musi być samowystarczalnym modułem w aplikacji:
  - config snapshot,
  - region detection/tracking,
  - health state,
  - debug crops,
  - normalized signals.
