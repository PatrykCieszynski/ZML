# ZML Game Bridge — MVP Roadmap

Updated: 2026-06-01

Ten plik jest roboczą roadmapą MVP po pierwszych realnych testach runów. Trzymamy tu tylko rzeczy otwarte albo częściowo domknięte, które nadal wpływają na poprawność danych, stabilność OCR albo ergonomię UI.

Legenda:
- `P0` — blokuje wiarygodne testowanie/run tracking.
- `P1` — mocno poprawia stabilność lub ogranicza ręczne naprawianie danych.
- `P2` — polish i ergonomia.
- `Later` — po MVP lub gdy będziemy mieć więcej danych.

---

## P0 — Mining correctness / data integrity

1. **Domknij lifecycle backendu Pythonowego w Electronie**
   - Brak orphan processów i wiszących DB connection przy zamykaniu UI/backendu.
   - Naprawić przypadki `Waiting for background tasks to complete`.
   - Electron docelowo powinien orchestrate start/restart/close `game-bridge`.

2. **Drop + segment correctness**
   - Segment tworzy się dopiero przy poprawnym `MiningDropEvent`, nie przy samej zmianie modes/ammo.
   - Segment jest statystycznym bucketem setupu w ramach runu, nie pojedynczym chronologicznym epizodem.
   - Jeśli drop ma ten sam setup hash co dowolny segment w aktualnym runie, dopinamy go do tego segmentu zamiast tworzyć duplikat.
   - Jeśli kiedyś będziemy potrzebować chronologii zmian setupu, dodać osobne `segment_episodes`, ale nie mieszać tego z agregacją segmentów.
   - `ammo_per_drop = 0` traktować jako invalid: użyć ostatniej sensownej wartości albo fallback z mode mask.
   - Drop z kosztem ammo/probes równym 0 nie powinien powstać jako poprawny mining drop.
   - Zmiana finder/ammo/mode/probes wpływa na segment dopiero przy kolejnym valid dropie.
   - Extractor zostaje globalny, nie segmentowy.

3. **Event context completeness**
   - `MiningDropEvent` powinien mieć `run_id` i `segment_id`.
   - `MiningNoResourcesEvent`, `MiningHitHintEvent`, `MiningClaimCreatedEvent`, `MiningClaimDeedReceivedEvent` też powinny mieć `run_id` / `segment_id`, jeśli da się je ustalić.
   - Event log ma być awaryjnym mechanizmem rekonstrukcji, więc durable eventy nie mogą być całkiem oderwane od runa.

4. **Claim lifecycle hardening**
   - Active claimy muszą wygasać, jeśli przekroczą expected expire.
   - Maintenance worker w runtime co jakiś czas oznacza expired przez DbWriter, bez zewnętrznego crona.
   - Extract miss albo brak OCR findera nie może zostawiać wiecznych active claimów.

5. **Loot totals zamiast spamowania event loga**
   - Nie zapisywać każdego `ItemReceived` jako durable event w main event log.
   - Dodać `run_item_totals` i `segment_item_totals`.
   - DbWriter robi `UPSERT` po każdym `ItemReceivedSignal`.
   - SSE wysyła debounced `loot_totals_updated`, maksymalnie raz na sekundę.
   - UI pokazuje totals jako źródło statystyk.
   - Recent loot history ograniczyć do ostatnich 25 eventów jako widok operacyjny.
   - `claim_item_totals` zostawić na później, gdy deed/claim flow będzie pewniejszy.

## P1 — OCR / position stability

6. **Finder crop recording cleanup**
   - Recording screenshotów findera był potrzebny do zebrania danych.
   - Po zebraniu wystarczającej liczby próbek można wyłączyć/wyczyścić crop recording z runtime.
   - Zostawić możliwość ręcznego debug capture później, ale nie jako domyślny przepływ.

7. **Profiling logs**
   - Profilowanie OCR mamy, ale logi trzeba rozdzielić.
   - Osobne profiling logi: `position`, `finder`, `deed`.
   - Jeden zbiorczy `profiling` log ze wszystkim.
   - Ułatwić porównanie capture/crop/preprocess/ocr/parse/emit bez mieszania domen.

8. **Compass latest-wins**
   - Max pending job = 1.
   - Drop stale frames.
   - Latest result wins.
   - Starszy OCR result nie może nadpisać nowszej pozycji.

9. **Position provider cleanup**
   - Finder coordinator ma brać pozycję z `position_provider`, nie z OCR snapshotu dołączanego do sygnału findera.
   - Wyczyścić legacy komentarze/zmienne `latest_position` / `finder_position` w OCR runnerze.
   - Poprawić logging `drop without position`, żeby był czytelny i nie gubił kontekstu.

10. **FinderPresenceCheck**
    - Zanim uruchomimy drogi OCR findera, zrobić tani check obecności findera.
    - Start MVP: dark/layout/template match małego stałego elementu findera.
    - Przykłady: kawałek nagłówka, ramki, ikonki, przycisku.
    - Jeśli finder zamknięty, pomijamy OCR findera.
    - Później: full-screen finder search albo manualny setup użytkownika.

11. **Finder mode classifier: Treasure states**
    - Treasure ma co najmniej trzy stany: active, inactive, disabled by planet/game.
    - Obecnie prawdopodobnie mylimy inactive z active, bo inactive treasure bywa jaśniejsze niż ore/enmatter.
    - Dodać osobne progi/test samples dla treasure.

12. **Planet / location trust**
    - Obsłużyć `/pos` event z chatu jako trusted position signal.
    - Przy dużych skokach Lon/Lat albo przejściu na unknown spróbować OCR planety/stanu.
    - Stany do rozróżnienia: normal planet, `unknown`, `space`, `pvp_zone`.
    - Nie robić agresywnej automatycznej zmiany planety bez potwierdzającego sygnału.

13. **Manual finder ROI calibration**
   - Electron overlay uruchamiany skrótem `Ctrl+Shift+F`.
   - User zaznacza prostokąt wokół findera.
   - Backend OCR używa zapisanego `finder_rect` zamiast hardcodowanego cropa.
   - Przygotować pod różne rozdzielczości, UI scaling i HUD layouty.

14. **Manual compass ROI calibration**
   - Electron overlay analogiczny do findera.
   - User zaznacza fragment kompasu używany przez OCR pozycji/kierunku.
   - Rozdzielić Lon i Lat jako osobne ROI.
   - Dwa presety: 5-cyfrowe i 6-cyfrowe koordy.
   - Docelowo 2 presety po 4 ROI, jeśli potrzebujemy osobnych pól/wariantów.

## P2 — UI / map / dashboard polish

15. **Loot UI**
   - Loot history ograniczyć do last 25 eventów.
   - Statystyki i tabele opierać o aggregated totals, nie o wszystkie raw item received events.
   - Naprawić przypadek, gdzie loot po paru godzinach wymagał restartu apki do synchronizacji.

---

## P3 — Schema cleanup / lower-risk cleanup

21. **Mining claim projection cleanup**
   - `position_z` / `depleted_z` można usunąć z `mining_claims`, bo mapa i korelacja MVP są 2D.
   - `range_m` zostawić raczej w eventach jako debug z findera.
   - Nie promować `range_m` do pola pierwszej klasy claim projection, jeśli nie jest potrzebne dla UI/logiki.

22. **Event log scope**
   - Event log jest awaryjny/debugowy, nie główna tabela analityczna.
   - Durable domain events zapisujemy, ale szum typu każde `ItemReceived` powinien iść do totals/projections.
   - Rebuild/projection z event loga powinien być możliwy dla krytycznych faktów: drops, no resources, hit hints, claim created/depleted, run/segment lifecycle.

## Kolejność pracy

### Batch 1 — Mining correctness

1. Drop + segment correctness.
2. `ammo_per_drop = 0` fallback/invalid.
3. Event context completeness: `run_id` / `segment_id`.
4. Expired active claims maintenance.
5. Loot totals storage.

### Batch 2 — OCR hardening

6. FinderPresenceCheck.
7. Treasure states classifier.
8. Position provider cleanup.
9. Profiling logs split.
10. Compass latest-wins.

### Batch 3 — Calibration

11. Finder ROI calibration overlay.
12. Compass ROI calibration overlay.
13. Lon/Lat ROI split and 5/6 digit presets.
14. `/pos` chat event.
15. Planet/space/pvp-zone handling.

### Batch 4 — UI polish

16. Loot UI last 25 + totals.

## Later / po MVP

- Po profilowaniu OCR rozważyć przeniesienie ciężkich OCR pipeline’ów z wątków do osobnych procesów.
- Automatyczna zmiana planety, jeśli dostaniemy stabilne sygnały.
- History View dla claimów z zakresem dat.
- Export run/history do CSV/JSON.
- Więcej settingsów w UI:
  - Hz/interwał dla kompasu,
  - Hz/interwał dla deeda,
  - Hz/interwał dla findera,
  - czas aktywności kółek dropów,
  - progi OCR/classifierów.
- Po 1.0 rozważyć wydzielenie OCR do managed local worker process:
  - config snapshot,
  - region detection/tracking,
  - health state,
  - debug crops,
  - normalized signals.
